# master 自动部署设计

目标：推送到 `bupt-lxc/MyStarry-Blog` 的 `master` 后，自动更新 `http://81.70.231.92:8550/`；不修改其他项目，不覆盖留言、会话、限流或服务器运行密钥。

## 方案比较

1. **GitHub Actions 构建并通过专用 SSH 连接发布（推荐）**：测试和镜像构建在 GitHub 托管 runner 完成，服务器仅加载镜像和切换版本，适合当前 2 GB 内存服务器。无额外公网监听端口，无需镜像仓库凭据。
2. 服务器 webhook 拉代码并构建：需要额外入口，构建会争用现有项目资源，故不采用。
3. 服务器定时拉取 Git：实现简单，但更新有延迟、错误反馈较弱，故不采用。

## 触发与构建

- 工作流仅在 `master` 的 push 或对 `master` 手动重试时部署，不接受任意分支发布。
- 使用 Node 24、pnpm 11，运行现有测试、类型检查、作品集校验与 Astro 构建，再生成当前 Dockerfile 的 Linux 镜像。
- 构建使用公开站点地址，不注入 SSH 密码、留言管理密码、来源 HMAC 密钥或数据库文件。
- 镜像使用完整 Git commit SHA 标记，并附带该 SHA 标签；静态文件与镜像打包为一个校验和可验证的发布包。
- GitHub 部署并发串行，不取消正在切换的发布；服务器另加文件锁防止并发手动操作。

## SSH 与服务器边界

- 为本仓库建立专用部署账号和 Ed25519 密钥。私钥保存为 GitHub 仓库 Actions Secret，固定服务器主机公钥校验，不使用 SSH_PASS。
- SSH 密钥限制为固定发布命令，禁止交互 shell、端口转发、代理转发、PTY；该账号不进入 docker 组。
- root 所有的服务器发布程序只接受明确的 commit SHA、发布包 SHA-256 和标准输入数据，验证参数、包大小及归档路径后才处理。
- 发布程序只操作既有 `astro-bento` Compose 项目的 `app` 和 `web`；继续公开 8550，Node 不公开端口。
- 自动发布使用服务器已有 Compose、Nginx 配置和 `.app.env`；不允许发布包替换这些文件。未来基础设施变更由单独维护步骤处理。
- 加载前校验镜像归档只带本网站的预期 SHA 标签，避免覆盖其他项目镜像标签。

## 数据保护、切换与回滚

- `data/guestbook.db`、WAL、持久会话、限流状态与服务器 `.app.env` 不属于发布包，不做同步、覆盖或清理。
- 发布前用现有 `VACUUM INTO` 命令创建一致性备份，并检查备份完整性；备份失败就终止发布。
- 保存旧 `current` 目标与旧镜像记录，验证镜像与静态文件均来自同一版本，再仅重建本网站容器。保留旧代码版本和数据备份。
- 检查 Nginx 配置、两个容器健康、首页、作品集、留言 API 和发布 SHA。失败则恢复旧镜像和 `current`，重建本网站容器；代码回滚不回滚数据库。
- 比较其他容器的 ID/启动时间与原 Nginx 校验和，确认没有触碰原有项目。无全局 Docker prune、compose down、数据库 restore 或共享端口改动。
- 发布包加载后删除该次临时归档，保留发布记录；不自动删除数据库、备份或其他项目的镜像。

## 验收与交接

- 本地测试参数/路径校验、发布包白名单、镜像标签边界、失败恢复，以及真实数据库保留行为；复用现有 20 项测试。
- 使用一次真实的 `master` 推送触发 Actions，从运行日志确认构建、上传、切换和验收成功。
- 验收前后对留言库内容和其他项目进行核对；若当前没有真实留言，使用可追踪的临时验收留言，在发布后确认保留再通过管理 API 清理。
- 文档记录 GitHub 变量/Secret 名称、专用账号权限、手动重试、回滚命令、域名切换和部署脚本升级方式。
- 自动部署不会改写现有网站内容或上线方式之外的配置。最终保留 8550 预览和 noindex；备案后同时更新公开构建地址与服务器运行地址。
