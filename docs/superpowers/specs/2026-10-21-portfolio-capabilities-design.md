# 二期作品集：能力分区与项目卡片设计

日期：2026-10-21（北京时间）

状态：页面结构、跨方向展示和卡片层级已在讨论中确认；本文件供书面审阅，确认后进入实施计划。

## 1. 目标与范围

作品集首先说明李星辰具备哪些核心能力，再通过具体项目呈现个人贡献及成果。招聘方应当能快速识别三个并列方向，并沿任一方向找到对应证据：

1. 全栈开发与项目落地。
2. 大模型应用与智能体。
3. AI 训练与推理优化。

本轮调整独立作品集总览 `/projects/`、共享项目卡片、相关项目元数据，以及详情页的能力标识、章节锚点和返回入口。首页继续作为个人主页，保留现有作品集入口。

沿用 Astro 内容集合、Markdown 详情、图片画廊、全站主题和样式切换。博客、留言板、技术栈面板、数据库、服务器配置和自动部署流程保持现有职责。本设计的文档提交只保存到本地 Git；后续实现和上线属于实施阶段。

## 2. 已确认的选择

| 决策 | 确定方案 |
| --- | --- |
| 能力主次 | 三块并列，等权展示 |
| 总览组织 | 三张能力总览卡＋三个始终展开的项目分区 |

| 设计讨论 | 文字讨论，完整设计稿审阅后再编写实施计划 |

曾比较能力分区、三个 Tab、平铺列表加筛选三种方案。选择能力分区，是为了让初次访问者无需切换即可看到完整能力轮廓；本轮以页内锚点组织浏览，三个分区在 HTML 中完整呈现。

## 3. 页面信息结构

阅读顺序如下：

```text
返回首页
作品集标题与一句个人定位
三张等权能力总览卡
全栈开发与项目落地：说明 → 完整项目卡片
大模型应用与智能体：说明 → 完整项目卡片 → 关联实践
AI 训练与推理优化：说明 → 完整项目卡片
返回首页／阅读博客
```

页面主标题使用“项目作品集”。定位文案为“从业务系统交付，到智能体应用，再到模型训练与推理优化。”总数按独立项目计算，当前为“3 个能力方向 · 8 个项目”，关联入口不重复计数。

### 3.1 能力总览

| 方向 | 能力说明 | 关键词 | 分区锚点 |
| --- | --- | --- | --- |
| 全栈开发与项目落地 | 把业务需求转化为可上线、可维护的产品。 | 需求与架构／前后端开发／部署运维 | `fullstack` |
| 大模型应用与智能体 | 让模型结合知识、工具和协作流程完成任务。 | RAG／工具调用／多智能体编排 | `agents` |
| AI 训练与推理优化 | 围绕模型效果、运行效率和算力适配进行优化。 | 安全对齐／异构适配／性能评测 | `training-inference` |

桌面三张卡等宽、同级标题、相同信息结构；移动端纵向排列，保留方向名称与说明。整张能力卡是单一页内链接，点击或按 Enter 定位对应分区。锚点写入 URL，可复制、刷新和通过浏览器返回恢复；无 JavaScript 时仍可正常浏览。

分区开头显示方向名称与一句说明，随后直接呈现项目。三个方向采用相同字号、间距和卡片规格；分区长度由实际项目数量决定。

### 3.2 主归属与顺序

主归属依据项目最能证明的核心贡献，保持每个项目唯一。分区顺序固定为全栈、智能体、训推；分区内沿用现有 `order` 的相对顺序：

| 分区 | 完整项目卡片顺序 | 独立项目数 |
| --- | --- | --- |
| 全栈开发与项目落地 | POMP → 华小博 → 保利赛事 | 3 |
| 大模型应用与智能体 | 新华医疗 NL2SQL → 奥迪车辆智能诊断 | 2 |
| AI 训练与推理优化 | AISHPerf → 海光 DCU 图像水印 → 移动多轮对话安全对齐 | 3 |

项目 slug、现有详情 URL、时间与合作背景保持原有口径。新增分类不改变项目身份，也不将一项合作拆成多个项目以增加数量。

主分区呈现完整卡片。其他相关分区在完整卡片列表后展示“关联实践”，每条包含项目名称、该方向的具体贡献摘要和章节链接。采用轻量文字行，视觉权重低于完整卡片；有实际关联时才显示此区域。

详情页顶部显示主能力及已配置的次能力，正文、目录、图片放大和完整外链继续复用。顶部和页尾的“返回作品集”指向该项目主分区，例如 `/projects/#fullstack`；关联入口已明确标注来自哪个项目，进入详情后可直接阅读对应贡献。

## 5. 单张项目卡片

### 5.1 桌面与移动端布局

桌面采用左图右文，封面约占三分之一，文字约占三分之二。手机端封面在上、文字在下，阅读顺序一致。高度由内容自然决定，在文字放大及窄屏下允许换行。

封面使用统一容器、留白和边框规则。有截图时展示一张代表性截图，优先完整容纳关键内容；竖长截图按容器缩放，完整原图留在详情页。无截图时使用统一项目名称封面，不补造产品截图。

### 5.2 信息层级与数量

| 层级 | 内容 | 数量与表现 |
| --- | --- | --- |
| 项目身份 | 合作背景、时间、项目名称 | 背景与时间弱化；名称是卡片主标题，页面中使用分区标题之后的正确标题层级 |
| 一句话问题 | 项目解决的实际问题 | 常见桌面宽度约两行；通过编辑控制长度，窄屏与放大后完整换行 |
| 我的贡献 | 个人负责范围、关键动作或设计决策 | 初始八个项目各两项，动作开头；元数据允许一至两项 |
| 项目成果 | 主成果、可选补充成果 | 主成果一项，关键数字或结论突出；补充成果最多一项，普通文字显示 |
| 辅助信息 | 技术标签、可选次能力入口 | 技术标签最多三个，次能力入口只在有跨方向贡献的项目出现 |
| 操作 | 查看项目详情、可选源码入口 | 查看详情为主操作；卡片最多展示一个源码链接，其余外链放详情页 |

摘要、贡献和成果均完整可读，不以固定高度裁切或省略号隐藏关键条件。列表只选择最有代表性的成果，详情继续保留完整职责、技术链路及其他成果。

项目标题、封面和“查看项目详情”进入同一详情地址；源码入口是独立链接。卡片外壳提供整体悬停反馈，所有实际操作使用语义化链接，交互元素互不嵌套。

### 5.3 贡献与成果的写作口径

“我的贡献”描述个人承担的动作，如独立交付、查询架构设计、任务执行适配、分支采样与优化；“项目成果”描述在该项目中取得的结果。团队平台整体数据与个人独立贡献保持边界，所有表述依据现有项目材料和已确认的 v2 简历。

成果保留条件、样本和单位。例如“View 命中场景：7 min → 20 s”“Top-5 召回率提高 37 个百分点”“1080p 编码：1.12 → 0.20 秒／图”。条件随指标直接显示，不藏在悬停提示里；百分比与百分点沿用原始口径。

主成果可以是规模、效果、效率或有依据的交付结论，不要求每个项目都填写数值。详细证据继续在正文展开。

## 6. 视觉与交互一致性

- 继续使用现有 `--primary-*`、`--darkslate-*` 等主题变量和全站卡片体系，尊重用户已经保存的主题与样式偏好。三个方向通过名称、编号和统一风格图标区分，使用同一主题强调色。
- 能力卡与项目卡沿用全站边框、背景、圆角和当前样式的表现；主成果与详情入口使用同一强调色，辅助标签保持较低权重。
- 悬停以轻微描边、高亮和现有轻量动效为主；键盘聚焦提供同样明确的可见反馈。主要信息与操作在触屏上直接可见。
- 页内定位保留适当顶部留白。减少动态效果偏好下使用即时定位，关闭新增位移动效；现有全站声音开关及动效门控继续生效。
- 本轮使用总览卡页内导航，保持三个分区展开；不另加 Tab、搜索、筛选、吸顶导航或新的动画组件库。

## 7. 内容模型与组件边界

### 7.1 内容来源

沿用 `src/data/projects/*.md` 的八个内容条目。现有 `slug`、`title`、`context`、`period`、`summary`、`role`、`tags`、`order`、封面与 `links` 继续承担原有职责。摘要在列表与详情间共用，完整角色说明保留在详情。

为表达已确认的设计，元数据增加：

| 字段 | 约束与职责 |
| --- | --- |
| `primaryCapability` | 必填，固定为 `fullstack`、`agents`、`training-inference` 之一 |
| `secondaryEvidence` | 可选数组，缺省为空；每项含 `capability`、`title`、`summary`、`anchor`，形成卡片次能力入口和其他分区的关联实践 |
| `card.contributions` | 一至两条非空个人贡献；初始八个项目各两条 |
| `card.primaryOutcomeId` | 必填，指向本项目一个成果 |
| `card.secondaryOutcomeId` | 可选，指向另一个成果 |
| `card.tags` | 一至三个标签，必须来自本项目完整 `tags` |
| `card.sourceLinkIndex` | 可选，从 0 起的整数索引，指向现有 `links` 中用于卡片展示的源码项；缺省不显示源码入口 |

`outcomes` 从字符串数组整理为带稳定 `id`、完整 `text` 和可选 `emphasis` 的对象数组。`emphasis` 必须是 `text` 中实际存在的唯一片段，用于强调数字或结论；列表与详情共同读取同一条成果文字。主、次成果通过 ID 选择，指标条件属于完整文字的一部分。此次整理保留原成果含义与所有需保留的条件，其余技术细节继续放在 Markdown 正文。

AISHPerf 的卡片源码入口选择评测框架源码；选型智能体源码和测试入口在详情继续保留。其余项目有现有源码时选择该项，没有时省略。

### 7.2 展示职责

- 能力定义集中维护三个方向的 ID、名称、说明、关键词和顺序。
- 作品集分组逻辑接收已验证的项目内容，按主能力分组并沿用 `order` 排序；从次能力数据派生关联实践，计数只使用唯一项目。
- 能力总览组件输出页内导航；分区组件负责标题、说明、项目列表与关联实践。
- `ProjectCard` 只接收一个项目及其展示数据，呈现统一的信息层级；成果文本与强调规则在列表、详情共用。
- `ProjectLayout` 继续负责详情布局、目录、完整内容和图片画廊，增加能力入口和主分区返回链接。关联信息不在多处手工复制。

具体改动集中在现有作品集页面、组件、内容集合与项目校验模块；共享样式调整限定在本轮需要的主题兼容和交互表现。

## 8. 校验、降级与兼容

- 构建时校验主分类合法且唯一、次分类与主分类不同、次分类不重复、贡献与标签数量符合约束、成果 ID 唯一且引用有效、主次成果不同、源码索引有效。
- 关联锚点必须属于本项目已渲染详情中的有效且唯一 ID；跨项目总览入口和详情链接在构建检查或产物检查中验证，错误阻止发布。
- 既有 slug 唯一性、图片引用和外链协议检查继续生效；错误标明项目及字段，便于直接修改 Markdown。
- 缺少可选封面、源码、补充成果或次能力时，组件自然收拢相应区域。无关联实践的分区不渲染空标题。
- 缺图项目使用文字封面；图片预留尺寸并保留有意义的替代文本。图片加载失败时链接及文字内容仍可使用。
- 三分区、项目卡片和关联入口为静态 HTML；页内定位及基本导航在 JavaScript 不可用时可使用。
- 网站继续使用现有发布流程。当前阶段只提交设计文档到本地；后续上线继续使用 8550，沿用既有数据库与运行密钥保护措施。

## 9. 验收标准

1. `/projects/` 首部直接展示三块等权能力，三个项目分区始终完整可浏览，桌面与手机均可理解分类。
2. 八个项目各有且仅有一张完整卡片，主分区和顺序符合本设计；总计为八个项目，关联实践不增加项目数。
3. AISHPerf 和华小博在智能体分区各有一条关联实践，并在其完整卡片中显示次能力入口；所有入口直达正确章节。
4. 卡片以问题、个人贡献、主成果为主要阅读内容；初始项目各两条贡献、最多两项成果、最多三个技术标签和一个源码入口。
5. 指标、条件、单位与现有材料一致，AISHPerf 两条工作线保持边界；详情保留完整内容和全部现有外链。
6. 宽屏左图右文，窄屏上图下文；检查 1440px、768px、390px 和 320px 视口，以及文字放大后的换行，无正文裁切和页面横向溢出。
7. 验证默认黄色 Neon、另一组颜色和非 Neon 样式；主题偏好在刷新与切页后保持，分类没有独立硬编码配色。
8. 键盘可操作所有入口，焦点明确；触屏可直接访问主要信息，减少动态效果设置有效，无 JavaScript 时基础阅读和导航可用。
9. 现有项目 URL、图片画廊和目录继续可用，首页作品集入口有效；新增项目内容校验、类型检查及构建通过。
10. 以有针对性的测试验证分类、唯一计数、关联派生、成果选择与无效引用；通过渲染产物检查或浏览器验证锚点、响应式与主题交互。实施计划再确定具体命令与执行顺序。
